Case 03 · QLoRA on a real LLM

Quantize the base to 4-bit, train a tiny LoRA adapter on top — fine-tune an 8B model on a free GPU.

1 · Quantization: fewer bits, smaller model

📖 What is quantization, and what is NF4?

What am I looking at?

Each bar pair shows one model weight. The orange bar is the true fp16 value (16 bits = 65,536 possible levels). The green bar is what you get after quantizing — rounding to the nearest level available at that bit width.

What does the Bit width slider do?

  • 16-bit: no quantization — green matches orange perfectly. Full memory cost.
  • 8-bit: 256 levels. Green is very close to orange. Model is half the size.
  • 4-bit: only 16 levels. Some rounding visible, but model is 1/4 the size. This is what QLoRA uses.
  • 2-bit: only 4 levels. Very lossy — too aggressive for most uses.

What is NF4 (Normal Float 4)?

NF4 is a 4-bit format designed for neural network weights, which are roughly normally distributed (bell curve). Instead of spacing the 16 levels evenly, NF4 packs more levels near zero (where most weights live) and fewer at the extremes. This gives lower error than naive 4-bit for the same memory cost.

What is double quantization?

Quantization stores a scale factor per block of weights. Double quantization quantizes those scale factors too — saving another ~0.4 GB on a 7B model. Free accuracy-wise.

How it connects to the capstone

Quantization is how you fit a big model on a small GPU. For the self-driving capstone, this means you can iterate on fine-tuning experiments on a single affordable GPU instead of renting expensive multi-GPU clusters.

📖 Where does all the VRAM go?

What are the stacked bars?

Each bar is total GPU memory for one training strategy. The segments show what eats the memory:

  • Weights: the model itself. fp16 = 2 bytes/param. 4-bit = 0.5 bytes/param.
  • Optimizer state: Adam keeps momentum + variance per trainable param = 2 extra fp32 numbers = 8 bytes each. Full fine-tune: all params are trainable. QLoRA: only LoRA params (~0.5% of total).
  • Gradients: one fp16 number per trainable param = 2 bytes each.
  • Activations: intermediate values saved for backprop. Roughly proportional to batch size and sequence length. We estimate ~1-2 GB here; gradient checkpointing can halve it.

What does the Model size slider do?

Scales everything: weights, optimizer, gradients all grow linearly with parameter count. Watch how Full FT explodes past any consumer GPU while QLoRA stays under 16 GB even at 13B.

Why Full FT is 4x the weight memory

Weights (2B/param) + optimizer (8B/param) + gradients (2B/param) = 12 bytes/param vs 2 for inference. A 7B model: 14 GB just for weights → ~84 GB to train. Nobody does this on one GPU.

Why QLoRA wins

Weights in 4-bit (~0.5B/param) + optimizer only for LoRA params (~0.5% of total) + gradients only for LoRA. The big base model is frozen and compressed — the expensive per-param costs apply only to the tiny adapter.

3 · The QLoRA pipeline: load → freeze → adapt → train → merge

The five steps in code: BitsAndBytesConfig(load_in_4bit=True) → AutoModel.from_pretrained(..., quantization_config=bnb) → LoraConfig(r=8, ...) → get_peft_model(model, lora_config) → SFTTrainer(...).train() → model.merge_and_unload()
📖 Walk me through each pipeline step

Step 1: Load in 4-bit

BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4", bnb_4bit_compute_dtype=torch.bfloat16, bnb_4bit_use_double_quant=True)

This tells HuggingFace: when loading weights, quantize them to 4-bit NF4 on the fly. The model lands on the GPU already compressed. compute_dtype=bfloat16 means matrix multiplications happen in bf16 for speed/accuracy, even though storage is 4-bit.

Step 2: Freeze

The 4-bit weights are automatically frozen — bitsandbytes marks them as non-trainable. You can optionally call prepare_model_for_kbit_training(model) which also enables gradient checkpointing and fixes layer norms to fp32 for stability.

Step 3: Attach LoRA

LoraConfig(r=8, lora_alpha=16, target_modules="all-linear", lora_dropout=0.05)

get_peft_model(model, config) wraps each targeted layer with a LoRA adapter. Now model.print_trainable_parameters() shows ~0.5% trainable.

Step 4: Train

SFTTrainer from trl handles tokenization, batching, and the training loop. Only the LoRA params get gradients and optimizer state.

Step 5: Save / Merge

model.save_pretrained("my-adapter") saves just the adapter (~10-50 MB). model.merge_and_unload() folds it back into the base for deployment.

How it connects to the capstone

Each data update in the self-driving scenario becomes a new adapter: cheap to train, cheap to store, cheap to swap. You can keep one adapter per data batch and load whichever you need — the starting point for fighting catastrophic forgetting in Case 05.
